## 已确认缺陷（以下保留修复前的分析）

### 1. IT-692 USB 串口匹配遗漏

固件存在 IT-694 的 `1286:4e3c` 匹配，但缺少 IT-692 `3505:0003`。这直接解释了“能经 4G 联网，但状态显示未检测到”。

修复源码：
[783-usb-serial-option-add-tastek-it692.patch](F:/Workspace/immortalwrt-dtu/target/linux/generic/hack-6.18/783-usb-serial-option-add-tastek-it692.patch)

仅匹配 vendor-specific 接口，避免与 RNDIS 抢占。已通过真实内核树 patch dry-run，并验证了对应动态匹配的现场效果。动态匹配仅保存在当前内核运行状态，重启后会失效；没有刷入永久修复固件。

### 2. 平台终端空闲后丢失序号状态

输入 ACK、输出序号、终端归属均使用 120 秒 TTL；旧 keepalive 只续期归属。用户空闲超过 TTL 后，归属仍有效，序号却从默认 0 开始校验，下一次合法输入/输出就被判乱序。

此前修复已让归属、输出队列、输入 ACK、输出序号一起原子续期，并校验节点及终端归属。旧平台尚未部署此修复。

相关代码：
- [terminal-state.h](F:/Workspace/iot-engine/service/features/edge/terminal-state.h)
- [gateway.h](F:/Workspace/iot-engine/service/features/edge/gateway.h)，`pumpTerminal`、`saveTerminalDataAck`、`saveTerminalData`
- [terminal-state-test.ts](F:/Workspace/iot-engine/tests/terminal-state-test.ts)

隔离 Redis 回归测试将 TTL 缩为 2 秒，复现旧逻辑下一条 ACK/output 返回 -1；新逻辑超过原 TTL 后仍接受连续序号。也验证真实序号跳跃仍被拒绝、旧 owner 不能续期新 session、旧协议不会被强行创建序号。

### 3. 终端错误扩大成节点主连接故障

`saveTerminalDataAck` 和 `saveTerminalData` 遇到序号不匹配直接抛异常。异常沿节点 `connect` 处理循环向外传播，导致节点主 WebSocket 关闭，而不是仅关闭出错终端。这与 10:07:13 现场日志吻合。

现已保留严格序号校验，将失败限制在相应 terminal_id，通知浏览器和节点关闭该终端，保留遥测及其他终端连接。

### 4. 新版 300 秒心跳与固件 90 秒应用超时冲突

当前平台源码 `HelloAck` 下发 heartbeat_interval_sec=300。固件 `application_timeout_ms()` 虽按心跳的三倍计算，却封顶 90000ms；只有收到有效应用 Envelope 才刷新此期限，WebSocket 控制帧 pong 不会调用这条路径。

在没有其他应用入站消息时，首次心跳计划在 300 秒，固件却会在 90 秒认定应用失活并重连。打开终端时的 20 秒 resize 保活或持续命令可能掩盖此问题。

使用实际 `edge_ws.c` 超时函数与 `edge_retry.c` 编译运行隔离探针，结果：

```text
heartbeat_seconds=300 application_timeout_ms=90000 timed_out_at_90s=1 first_heartbeat_ms=300000
```

此项是当前源码的可复现兼容缺陷，不能直接认定是现场这次持续离线的原因：故障前现场记录实际约每 5 秒上报，旧平台源码也下发 5 秒。

## 固件自恢复缺口：代码确定，现场触发未证实

### 5. 关闭终端可能无期限阻塞主事件循环

`edge_terminal.c::terminate_and_reap()` 先发送 SIGHUP 并短暂轮询，随后 SIGKILL，再执行阻塞 `waitpid(child, NULL, 0)`，没有最终时间上限。

`schedule_reconnect()` 和终端关闭处理会同步调用它。若子进程卡在不可中断内核 I/O、不能立即响应 SIGKILL，整个事件循环可能等住；心跳、重连定时器和状态刷新都会停止。

需要改为有界、非阻塞回收，并保留待回收 PID，避免僵尸和容量泄漏。现场没有 `/proc/<pid>/wchan`、线程栈或 strace，不能宣称已经证明这次卡在 waitpid。

### 6. 现有看门狗不能识别主进程假活

`network-watchdog` 仅判断 `/usr/sbin/edgenode` PID/cmdline 是否存在，以及两个公网地址是否可 ping；procd respawn 也只处理进程退出。

如果主进程仍存在、事件循环卡住，而外网仍可 ping，看门狗不会恢复该进程。采集 worker 的 120 秒 watchdog 运行在主事件循环内，也无法救活已经卡住的主循环。

应由独立进程检查由主事件循环推进的单调时间心跳，检测停止推进后恢复服务。不能简单以“平台离线”替代主循环健康检查，否则平台维护或链路故障会导致误重启。
