# 边缘节点读取间隔修复与联合发布

用户要求实际设备读取遵守配置，不再固定 1 秒；并明确选择与正在开发的 DTU 功能合并后统一构建发布。本次不单独部署平台、不构建独立固件版本，也不刷写设备。

## 配置与兼容

平台 `readInterval` 以秒配置，仍下发到 `report_interval_sec`。`io_interval_ms` 下发为 0，新固件据此将实际读取周期设为配置秒数乘以 1000；显式非零值支持 1000–3600000 ms。状态页显示解析后的实际周期。

原 0.3.49 固件仅接受 0 或 1000，且两者都按 1 秒执行。采用 0 可保证平台先更新时旧固件不拒绝整个配置；旧固件必须升级后才能改变读取频率。新固件收到旧平台的显式 1000 时仍保持 1 秒。字段编号、类型和消息格式不变，旧固件下载及升级协议不变。

| 平台 / 固件 | 原固件 | 新固件 |
| --- | --- | --- |
| 原平台（显式 1000） | 1 秒 | 1 秒 |
| 新平台（0，附配置秒数） | 仍为 1 秒，等待升级 | 遵守配置间隔 |

联合发布时应升级平台与固件，并确认节点应用了新的配置版本。不能仅凭平台配置已下发，就宣称旧固件已经按新周期运行。

## 固件实现

- `edge_device_runtime` 保存每个设备的实际读取周期。每秒调度检查仅用于响应事件，不再意味着每秒执行一次读取。
- 调度延迟时跳过已错过的周期，不补发密集读取。
- 待处理控制命令可以在下一次调度检查执行并读回，不被 30 秒或更长的周期读取阻塞，也不改变原周期截止时间。
- SL651 主动上报不被改造成定时轮询。平台上报与已有控制命令快速上报逻辑保持原职责。
- DTU 功能仍在并行修改，本任务未提交或发布其未完成实现；协议注释及生成文件由 nanopb 正式生成器同步，未手改生成代码。

## 验证与待执行

为避开并行开发中的 DTU 源码，使用固件 HEAD 加本次采集修改生成隔离测试源。Release 主机构建保留测试断言（`-O3 -UNDEBUG`），配置、调度与状态测试验证 0、1 秒、5 秒、30 秒、3600 秒，拒绝越界值，并覆盖 5 种轮询协议、延迟调度及控制命令。

主机 CTest 首轮 19/20；失败的 `network_watchdog` 是隔离目录缺少基线脚本。补齐脚本后，与本次修改相关的 `edge_runtime`、`edge_config`、`edge_status` 及该失败项 4/4 通过，其余首轮测试已通过。日志为 `build/read-interval-ctest.log` 与 `build/read-interval-focused-tests.log`。

按用户安排，平台双平台 Release/CTest、包含 DTU 的整机固件构建、镜像校验和实机读取间隔验收留到联合发布。尚未在生产生效。
