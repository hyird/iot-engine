# SUMMIT DTU 二进制转发逻辑分析

## 分析对象与结论

继续分析用户提供的 `SUMMIT_DTU_IoT_R21.02-V2.7_D20260420.bin`，对象为解包后的 `/usr/sbin/at_cmd`。配置页面分析见 [固件配置拆解](edge-dtu-firmware-analysis.md)。

`at_cmd` 长度为 225,704 字节，SHA-256 为 `3666f6fe1276a76871688d7d36e40d341dc946d8e2c0326078a706547be76605`。

二进制控制流确认：程序以网络通道为单位持有 TCP 连接，转发规则选择目标通道，再使用目标通道已有的连接发送。普通 TCP Server 通道向已连接客户端广播；普通 TCP Client 通道使用一个已保存的连接描述符。串口上行会分发给所有配置为连接串口的网络通道。

这支持“南向接设备、北向接服务器、节点内部配置转发关系”的设计。南向可以是 TCP，而不只是串口；转发关系和实际连接必须分开建模。

## 方法与证据可靠性

- ELF 为小端 MIPS32r2，标记包含 `mips16`，无节表。主要业务函数实际采用 MIPS16，不能用普通 MIPS32 反汇编结果作证据。
- 使用 GNU Binutils 2.40 的 `mipsel-linux-gnu-objdump`，按 `-b binary -m mips:16 -EL --adjust-vma=0x400000` 解码，再依据 ELF 程序头、动态符号和重定位表标注导入函数及字面量池。
- MIPS16 分支和调用地址的最低位是指令集标记。例如调用目标 `0x407f75` 对应文件中实际起始虚拟地址 `0x407f74`。
- 完整反汇编为 `build/summit-dtu-analysis/at_cmd.mips16.txt`；关键函数已单独保存为同目录下的 `*.asm.txt`。字面量池混在代码区域内，不能把池中的反汇编文本当作可执行路径。
- 本文为静态控制流分析，没有启动第三方固件进程或执行网络、硬件测试。已经确认的分支行为和仍需运行验证的可靠性问题分别列出。

## 1. 路由字段确实控制目标通道

`0x41fa8e–0x41fab8` 读取 UCI 的 `socket_dtu_route`，通过 `%hhu` 写入：

```text
current_sys_config 基址 = 0x44731c
route[channel] = *(uint8_t *)(0x44731c + 5448 + channel)
```

网络接收路径在 `0x4040b2–0x4040ba` 调用 `socket_data_handle(channel)`。函数起点 `0x4076f8`，名称来自其自身日志字符串。

该函数从按通道索引的接收缓冲读取数据：

```text
buffer[channel] = 0x467ed8 + channel * 10245
length[channel] = *(uint16_t *)(0x4471ac + channel * 2)
```

`0x4079ee–0x407a02` 判断 `route[channel] == 4`。若是串口，进入串口队列路径；否则走目标网络通道路径。`0x407d94–0x407dac` 将 `route[channel]`、缓冲指针、长度作为参数调用网络发送函数。

省略 AT 命令、协议转换和缓存等分支后的等价描述为：

```c
on_network_payload(channel, bytes, length) {
    target = route[channel];
    if (target == SERIAL) {
        enqueue_serial(bytes, length);
    } else {
        send_or_queue_to_existing_channel(target, bytes, length);
    }
}
```

这里的发送参数没有“为该转发关系建立新 TCP 连接”的身份。多条关系选择同一目标通道时，复用的是目标通道的连接和发送资源。

## 2. TCP Client 使用已有连接

`socket_send` 位于 `0x407f74`，最终调用 `socket_send_d`（`0x40841c`）。普通 TCP Client 分支在 `0x408910–0x408934`：

```c
fd = client_fd[channel]; // 基址 0x4472e0，步长 4
send(fd, bytes + offset, length - offset, flags);
```

发送路径没有按南向来源重新执行 `socket()` 或 `connect()`。目标通道可以被不同转发调用使用，发送函数在 `0x408514–0x408526` 使用按通道索引的信号量串行化访问。

## 3. TCP Server 的默认发送是广播

在普通 TCP Server 分支，`0x4087d8–0x40883e` 遍历 1 至 10 的客户端槽位。每个槽位取出描述符，跳过负值，对有效描述符调用 `send()`：

```c
for (slot = 0; slot < 10; ++slot) {
    fd = server_client_fd[channel][slot];
    if (fd >= 0)
        send(fd, bytes + offset, length - offset, flags);
}
```

描述符表基址为 `0x4652f0`，寻址公式为 `base + (channel * 10 + slot) * 4`。实际 `send()` 调用位于 `0x40882a`。

因此，假设 A 为南向 TCP Server、B 为北向 TCP Client，配置 A → B、B → A：

- A 下的多个设备连接可以向 B 通道的同一个北向连接发数据。
- 默认模式中，B 返回并转发给 A 的数据会发送给 A 下的所有有效客户端。
- 这不是自动识别请求来源并返回给原设备的事务代理。
- “遍历十个槽位”是二进制中可确认的事实，不等于已经验证十客户端的吞吐、连接上限配置或异常行为。

## 4. 存在可选的客户端定向模式

`socket_sendid` 在 `0x420428–0x420440` 读取，写入 `0x448868`，即配置基址加 `5452`。样本默认值为 `0`，本次提取的 LuCI DTU 页面没有提供这个字段的编辑控件。

开启为 `1` 时：

- TCP Server 接收路径 `0x403e04–0x403e94` 在数据前加入 `%d,%d,`，两个值分别为从 1 开始的通道号和客户端槽位号；十号槽位有单独的前缀长度处理。
- TCP Server 发送路径 `0x40870c–0x4087d6` 解析数字字段，并用解析出的通道号及槽位号索引描述符表，进入定向发送分支。
- 示例形态为 `1,2,内容`，表示通道 1、客户端槽位 2。它是可选的带标识模式，不再是完全不改写载荷的原样透传。

该模式的文本解析、二进制零字节、分片、槽位重用及越界处理尚未完成运行验证，不能直接作为我们对外协议的兼容承诺。特别是槽位号不是稳定设备身份。

另外，`socket_recv_from_en` 使用配置基址加 `5453`，在发往串口时可增加 `+RECV` 提示；它与 `socket_sendid` 是两个不同开关。

## 5. 串口支持向多个网络通道分发

`user_data_handle` 的串口数据处理路径在 `0x4096fa` 初始化通道索引。`0x40970c–0x40971c` 判断每个通道的 `route[channel] == 4`，不满足就跳过；`0x40a1ca–0x40a1d6` 将索引递增并循环至四个通道处理完毕。

满足条件的普通在线网络通道，会在 `0x40a07a–0x40a086` 或 `0x40a15a–0x40a166` 调用 `socket_send(channel, bytes, length)`；其他分支可排队、转换或按协议模式发送。

因此串口可以由一个实际 I/O 入口持有，同时将收到的数据分发给多个网络通道。物理串口独占不意味着业务上只能绑定一个北向目的地。

## 6. 合流、回包和可靠性的边界

普通接收路径使用通道级缓冲；从多个 TCP 客户端接收到的数据进入同一通道的处理入口，关闭 `socket_sendid` 时不会自动附加客户端标识。默认发送路径也没有根据最后一次请求来源选择回包对象，而是上述 Server 广播或 Client 单连接发送。

还应注意两类不同关系：

- 多个客户端接入同一南向 Server 通道：默认回包广播已得到指令级证据。
- 多个独立通道 A、C 都转发到 B：两者可以共用 B 的连接，但 B 仍只有一个 `route[B]`。不能因此推断 B 的回包会自动反向分发给 A 和 C。

本次未把以下事项判定为通过：多客户端压力、断网重连、各客户端部分写入的独立进度、缓存满、平台离线及设备断电后的恢复。Server 广播代码使用同一个局部发送进度变量，不能据此承诺对每个客户端独立、完整交付。

## 对实现的直接影响

1. 南向资源和北向资源独立配置，转发规则引用通道。
2. TCP 连接归通道及所属运行对象持有；规则复用公开的发送能力，不重复建连，也不跨 Worker 转交连接。
3. 串口由一个运行对象独占，允许在该对象内按规则分发到多个北向连接；是否与主动采集共存须另行定义仲裁。
4. 明确提供单向或双向规则，并显式规定 TCP Server 下行是广播还是定向。
5. 原样透传默认不附加来源标识；需要多设备定向时，单独定义封装和设备身份，不能暗中添加字段。
6. 参考已确认的通道模型，自行实现可验证的背压、完整写入和资源恢复，不直接复制第三方二进制中的异常处理。
